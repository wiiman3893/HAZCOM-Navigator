APPLICATION DATA ARCHITECTURE — Hazcom Navigator
============================================================================

Primary builder: CRUD / Application Builder
Target platforms: android, ios, desktop
Data behavior: hybrid
Recommended storage: SQLite
Recommended stack: CLIENT-SPECIFIC — use each client definition below; do not apply one platform stack to every client.

RATIONALE
- SQLite keeps a structured relational database in one local file with no server, account, or network dependency.
- It is a strong fit when the application manages many searchable or related records while remaining local and portable.

DATA MODEL STRUCTURE
- Canonical ownership relationships define record containment. Numeric structural levels are retired legacy metadata and MUST NOT be used to infer application behavior.

IMPLEMENTATION NOTES
- Persist attachment metadata and stable paths in structured storage; keep large binary files in an application-managed attachment directory by default.
- Backups must package structured data, managed attachments, and a versioned restoration manifest.
- Represent change history with append-only change records instead of duplicating complete application state.
- Use soft deletion so accidental deletes can be restored before permanent purge.
- Treat alert-capable data as optional, user-configurable notification inputs. Do not hard-code alert timing, recipients, or delivery channels from the Constellation capability alone.
- Project architecture note: Company is the canonical Organization. Workers can read Company-wide hazard information; Work Area Assignment does not restrict hazard browsing. Work Area Product is the association between Work Area and Chemical Product and owns pairing-specific Quantity, Storage Location, and Added Date. Work Area Assignment is the association between Worker and Work Area and owns assignment/training requirement state. When an assignment is created, Training Required Since = Assigned Date. Adding a Work Area Product moves Training Required Since to that product's Added Date for every active assignment in that Work Area. A Training Event on/after Training Required Since makes that assignment current until another trigger occurs. HAZCOM Manager controls domain records only; Administrator additionally manages Accounts, Memberships, roles, and Company settings. For Accounts with several Company Memberships (especially Professional Plan purchasers), all Organization-scoped screens/actions operate in an explicit active Company context. Experience screens are shared where workflows converge; permission-bound controls are hidden when Access & Identity denies the operation. Client capability also gates actions: Windows is the full authoring client while mobile exposes only consumption plus configured limited capture. Time-based compliance state is evaluated against the current date: Work Area review is required when no HAZCOM Review exists or today is on/after next_review_due; otherwise it is current. Chemical Product SDS verification is required when no SDS Verification exists or today is on/after verification_due; otherwise it is current. HAZCOM Review, SDS Verification, and Training Event are append-only ordinary history; normal Manager/Administrator UI must not offer update/delete for those Event records. Physical-storage optimization is permitted where semantics are unchanged: an exactly-one ownership or single-reference linkage may be implemented as a direct foreign-key column on the child/association table instead of a generic relationship table when cardinality, referential integrity, stable identity, migrations, authorization traversal, and canonical relationship meaning are all preserved. This permission does not allow collapsing association Records, Event history, or domain concepts into their endpoints.

STORAGE TOPOLOGY
- Data behavior: hybrid.
- Local/client persistence foundation: SQLite.
- Android: local role=published-replica; persistence=SQLite + application-managed SDS files; offline=yes.
- iOS: local role=published-replica; persistence=SQLite + application-managed SDS files; offline=yes.
- Windows: local role=draft-authority; persistence=SQLite + Application-managed SDS files; offline=yes.
- Shared backend: Firebase.
- Shared structured data: Cloud Firestore.
- Shared managed files: Cloud Storage for Firebase.
- Draft/working authority: client-local; published/shared authority: shared-backend; movement=publish-revision.
- Explicit client/shared-backend choices are authoritative. Do not substitute MySQL/PostgreSQL merely because the project is Hybrid.
- Local persistence, shared structured data, managed files, and backup/export are separate architecture layers.
- Alert-capable data may require background/server evaluation when its authoritative source is remote; do not assume an open client is always responsible.

CLIENT / PLATFORM ARCHITECTURE
- The canonical domain model is shared. Client availability does not duplicate or redefine domain entities.
- Authorization answers who is allowed to perform an action. Client capability answers whether this client exposes that action. Both must permit an operation.
- Client/UI availability is never a security boundary; authoritative services and data-access rules must still enforce authorization.

CLIENTS
- Android [Android]: responsibility=consumption; localDataRole=published-replica; offline=yes
  Local persistence: SQLite + application-managed SDS files
  Capabilities/workflows: Search, browse Company work areas, emphasize assigned work areas, view SDS, view extracted product information, view own assignments and training status, record own training completion, favorites, recent items, synchronization, limited single-record SDS/product capture
  Platform integrations: Camera, QR/barcode reader, file/share import
  Notes: Consumption-first client. Work Area assignment personalizes the worker experience but does not restrict Company hazard/SDS browsing. Management actions appear only when both Access & Identity and this client's configured capability allow them.
- iOS [iOS]: responsibility=consumption; localDataRole=published-replica; offline=yes
  Local persistence: SQLite + application-managed SDS files
  Capabilities/workflows: Search, browse Company work areas, emphasize assigned work areas, view SDS, view extracted product information, view own assignments and training status, record own training completion, favorites, recent items, synchronization, limited single-record SDS/product capture
  Platform integrations: Camera, QR/barcode reader, file/share import
  Notes: Consumption-first client. Work Area assignment personalizes the worker experience but does not restrict Company hazard/SDS browsing. Management actions appear only when both Access & Identity and this client's configured capability allow them.
- Windows [Windows]: responsibility=authoring; localDataRole=draft-authority; offline=yes
  Local persistence: SQLite + Application-managed SDS files
  Capabilities/workflows: Company administration, work area management, user and assignment management, bulk SDS import, OCR and extraction, extraction review, duplicate detection, revision handling, SDS replacement, bulk operations, publishing, backup and export
  Platform integrations: Filesystem, drag-and-drop, file picker, scanner
  Notes: Windows is the primary management and bulk-ingestion environment. It supports complete HazCom authoring, SDS ingestion/review, worker/assignment management, publishing, reporting, backup, and export.

DATA MOVEMENT
- Mode: publish-revision
- Draft/working authority: client-local
- Published/shared authority: shared-backend
- Background synchronization: enabled
- Notes: Windows maintains working changes locally. Approved changes are published as versioned company datasets. Mobile clients compare their local revision with the published revision and download required updates rather than continuously synchronizing every edit.

SHARED BACKEND
- Provider/foundation: Firebase
- Authentication: Firebase Authentication with Google sign-in
- Structured data: Cloud Firestore
- Managed files: Cloud Storage for Firebase
- Notifications/messaging: Firebase Cloud Messaging
- Diagnostics: Crashlytics for Android/iOS; Windows diagnostics handled separately
- Notes: Cloud-hosted published company data is authoritative for distributed clients. Firebase does not replace the required local/offline databases.

IMPLEMENTATION BOUNDARIES
- Do not force feature parity across clients. Implement only the responsibilities and workflows assigned to each client.
- Local persistence, shared persistence, and synchronization are separate architecture layers. A client may use SQLite/files locally while a shared backend uses an entirely different database/file service.
- Do not replace a required local/offline store merely because a shared backend exists.
- When draft and published authority differ, preserve that distinction explicitly instead of treating every copy as equally authoritative.
- Platform integrations are implementation capabilities, not new domain entities unless the product separately models them as business records.

PLAN BUILDER / COMMERCIAL ENTITLEMENTS
- Commercial mode: paid; purchaser may be: account.
- Account identity is generic. Purchaser profiles describe how someone buys/uses the product; they are not Account types or security roles.
- Plan = bundle purchased. Charge = how money is collected. Entitlement = what the purchase unlocks. Usage Meter = measured commercial unit. Membership/Role = authorization inside an Organization.
- Never infer authorization from payer/coverage, and never infer billing responsibility from a Membership role.
- Runtime purchases/subscriptions are entitlement instances. Persist entitlement ownership and Organization coverage assignments separately from the reusable Plan definitions so coverage can transfer without moving domain data.
- Purchaser profiles: Customer: Purchases access to create and operate an Organization in this product.

PLAN: Customer Plan [primary]
- Purpose: Plan intended to end users with a single company role.
- Intended purchaser profiles: Customer
- Charge: Subscription; type=recurring; billing choice=ONE of the following options (not additive):
  - Monthly: USD 10 / monthly
  - Annual: USD 100 / annual
- Organization coverage: mayCreate=true; max=1; autoCoverCreated=true; transferAllowed=true; preserveMembershipsOnTransfer=true.
- Initial Membership role on Organization creation: Administrator.
- Entitled features/services: Active HazCom Navigator paid entitlement
- Lifecycle/access: trialDays=0; graceDays=14; expiration=export-only.
- Post-expiration retention: structuredDataDays=not specified; managedFilesDays=not specified; backupDays=14; finalBehavior=custom (Delete subscription backup copies after 14 days of non-payment. Do not infer deletion of canonical Company data or managed SDS files from backup deletion; their authoritative retention requires a separate explicit policy.). Access restrictions and data retention are separate policies.

- Charge: Subscription; type=recurring; billing choice=ONE of the following options (not additive):

COMMERCIAL / AUTHORIZATION BOUNDARY
- Organization coverage may transfer between plans or payers without moving the Organization data. Preserve Memberships unless the plan explicitly says otherwise.
- A person may hold a plan entitlement while belonging to zero Organizations; Organization Memberships are created only when needed for authorization.
