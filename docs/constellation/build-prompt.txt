PROJECT
Project name: Hazcom Navigator
Internal project ID: SS-2026-1764
Project type: custom-application
Status: idea
Target platforms: android, ios, desktop
Default data behavior: hybrid
Core description: Hazcom Navigator is an app that simplifies the hazcom process. It allows companies of all sizes to build HAZCOM programs and training of any complexity with a simple interface, including SDS scanning and training generation. Allows for simple 1910.1200 compliance. 
Project notes: HazCom Navigator uses Company as the access Organization and canonical business owner. Workers may browse Company-wide Work Areas, Chemical Products, SDS information, and Work Area Product records; a Work Area Assignment personalizes the worker's applicable training/work-area context but is not an authorization fence for hazard information. HAZCOM Managers manage HazCom domain data inside their Company. Administrators have the same domain-management capability plus Company, Account, Membership, and role administration. A Worker is a business record and may optionally be linked to an Account; Account identity remains separate. Windows is the primary authoring/bulk-ingestion client. Android/iOS are offline-capable consumption clients with limited single-record capture. Approved Windows changes publish versioned Company datasets to Firebase; mobile clients synchronize published revisions rather than every draft edit. Formal HazCom/program exports, PDF/handoff packages, SDS attachments, training output, and a rebuild/import package are required. After paid access ends, the configured grace/export-only behavior applies; subscription backup copies are deleted after 14 days of non-payment. Work Area review and SDS verification are time-based states: after the latest completion they remain current until the derived next-due date, then become required; absence of any completion means required. SDS Verification, Training Event, and HAZCOM Review are append-only ordinary history. Top-level management collections are scoped to the explicitly selected active Company.

- Alert-capable data sources are capability boundaries, not notification policy. The finished product should let users/product rules choose whether and how to alert; do not invent fixed timing, recipients, or delivery channels.
- Named managed-file slots use the managed attachment/file lifecycle with a stable slot key. Do not also persist the same file in a duplicate entity file column.
- Generic attachment requirements are per data type and remain separate from named managed-file slots.

- Reporting/generated outputs are projections over canonical records. Reports must not become a second source of truth.

EXPERIENCE / UI MODEL
- The canonical Data Model defines records, ownership, and relationships. It does not by itself dictate screen hierarchy.
- The Experience Model below is authoritative for screen composition, derived collections, summaries, interaction, and navigation where configured.
- Each navigationId is one canonical user action. Canvas edges and screen controls that reference the same navigationId MUST implement the same destination, relationship path, and context behavior; do not create a second independent navigation rule.
- Reuse canonical data types, fields, and relationships referenced here. Do not create duplicate UI-only domain entities.
- Derived queries are logical views over canonical records by default. Do not create duplicate persistence tables merely to render a dashboard unless materialization is explicitly required for scale.
- owned-descendants query scope means: start from the current screen record context, traverse canonical record-ownership relationships transitively, and return matching target records found in that ownership subtree.
- Context passing is authoritative: current-record preserves the source context, selected-record passes the clicked record, relationship-result scopes the destination through the configured canonical relationship, and none opens without record context.
- Collection means many records, Detail means one concrete record, and Dashboard means independently configured blocks around optional context. Do not silently substitute one screen semantic for another.
- Audience is a presentation-routing concept that references Access roles. It is NOT an Account type, Membership replacement, or independent authorization system.
- An Audience start screen chooses where that audience enters the same application. Reuse canonical screens across audiences whenever their workflows converge.
- Permission-bound data actions MUST be authorized by Access & Identity at the authoritative service/data boundary. Hiding or disabling a control is presentation only and MUST NEVER grant or substitute for permission enforcement.
- Evaluate permission-bound controls against the CURRENT RECORD/RELATIONSHIP CONTEXT and the configured Access scope (own organization, assigned records, linked business record, relationship path, etc.). A role having the verb somewhere is not enough; the current target/context must be in scope.
- Optional audience restrictions may further hide presentation elements, but they MUST NEVER broaden access beyond the canonical role permission rules.
