# Windows publication handoff

Updated September 26, 2026. See [Firebase schema-2 deployment handoff](FIREBASE_SCHEMA2_DEPLOYMENT_HANDOFF.md) and [current Work state](WORK_MODE_CURRENT_STATE.md) for the exact live revision IDs and unfinished security checks.

The native Reports & Export screen publishes one active Company's Windows SQLite draft through the existing schema-2 Functions: begin, deterministic chunks, trusted SDS upload, seal, paged validation, and finalization. The client writes neither published Firestore entities nor published Storage files directly. Readiness validates Company context/role/capability, relationships, SDS signatures/sizes/SHA-256, and manifest limits. BLOCKING disables Publish; WARNING permits existing contract-allowed gaps. The server repeats all authorization and completeness checks.

The attempt journal in `apps/windows/src/data/publication.ts` now keeps one initialized SQLite connection open. Repeated `Database.load`/`close` calls reused a closed pool in the native Tauri SQL plugin, producing `database is locked` and `attempted to acquire a connection on a closed pool`. The cached connection promise resets on initialization failure. After this fix, native SDS attach and readiness ran without the lock/pool failure.

`apps/windows/src/data/publication-workflow.ts` retains the user-scoped revision ID, parent and fingerprint, reconciles an ambiguous finalization response by manifest hash, and compares the local draft with the current revision's content hash. A real schema-2 publication committed revision 2 in the cloud but its immediate post-finalization pointer read briefly disagreed and the UI showed a false error; the next readiness correctly reconciled it. The workflow now retries that read four times with bounded delays before reporting failure. A second native publication to revision 3 displayed the normal success message. A missing native SDS OS error now maps to a useful reattach instruction. The temporary test-only Storage read probe was removed; no permanent UI feature was added.

The live synthetic Company `smoke-19c0423b-64d3-4138-9cf8-89fc162d1f54` reached 17 records/3 SDS. Temporarily renaming one synthetic SDS produced BLOCKING and a disabled Publish button; restoration returned READY. Revision 2 was published at `2026-09-26T11:41:10.584Z`, and revision 3 at `2026-09-26T11:54:29.162Z` after a Work Area description edit. Before revision 3, Reports displayed “Local changes have not yet been published.” Afterwards it displayed the matching current revision and disabled duplicate Publish.

The independent read-only cloud integrity script `scripts/live-schema2-receiver.mjs` in the acceptance worktree used Firebase CLI OAuth to read the published manifest/entities and actual Storage SDS bytes into a separate SQLite database. It proved a corrupted SDS download left revision 2 active and a clean retry atomically activated revision 3. This privileged transport does not prove Firebase client Rules access; the signed-in native Firebase SDK separately proved authorized SDS retrieval for one revision-2 PDF, while anonymous URLs returned 403.

Validation after source fixes: `npm run test:windows:publication` 6/6, `npm test`, `npm run test:firebase` 16/16, `npm run build`, Firebase Functions build, and `HAZCOM_SCALE_SIZES=small npm run test:scale` passed. The schema-2 small emulator harness published 140 records/20 SDS and imported a clean replica. Medium/Large/Stress measurements remain in [scalable publication handoff](SCALABLE_PUBLICATION_HANDOFF.md) and were not rerun.
