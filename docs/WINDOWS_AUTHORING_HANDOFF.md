# Windows authoring core handoff — 2026-09-22

The native Windows workspace now supports Company-scoped authoring for Work Areas, Chemical Products, Work Area Products, Workers, Work Area Assignments, SDS Verifications, HazCom Review Events, and Training Events. It uses the existing Constellation SQLite schema and relationship IDs. Company identity, active membership, and Manager/Administrator permission are rechecked against Firebase before operations; Members do not open the authoring database. Company settings and memberships remain trusted Firebase Function operations, available only to Administrators.

`packages/authoring` owns validation, Company-scoped repository operations, derived status, filters, and summaries. Its SQL adapter runs writes as atomic batches with an authoring version guard and change history. `database/migrations/003_authoring.sql` adds local version and SDS integrity metadata. The Tauri adapter in `apps/windows/src/data/authoring.ts` supplies SQLite, live authorization, and managed PDF storage. The native UI is `apps/windows/src/AuthoringWorkspace.tsx`; it provides CRUD, relationships, historical events, search/filter, Trash/restore, SDS import/preview, and Company administration. Record IDs are stable. Events are append-only. Adding a Chemical Product to a Work Area updates the training-required date of its active assignments.

Draft SDS files are copied into app-managed local storage. SQLite records their owner, relative path, size, and SHA-256. Replacements retain local history; preview verifies size and hash. These are draft files until explicit publication. The Reports & Export screen explains publication status but has no publish control. The existing publication/replication service and Firebase backend were not redesigned or deployed in this authoring slice.

The automated checks cover relationship and tenant isolation, role/revocation gates, event rules, soft-delete behavior, SDS integrity, representative Company workflows, performance fixtures, and browser rendering. Native authenticated manual acceptance remains a separate validation step after the preserved source checkpoint. See `docs/windows-authoring-measurements.json` for synthetic service timings. A native acceptance pass must separately verify the Google-return flow and actual persisted records after app restart.
